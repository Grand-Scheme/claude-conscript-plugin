## 1. Tailoring-mechanism decision: HYBRID (config file, interview-generated on first need)

**Decision:** Keep `study-config.md` — a plain-Markdown config file in the **project root** —
as the single project-specificity mechanism (Marc's option a). It is **generated by an
intent-stated interview the first time any skill needs it** (Marc's option b), and remains
hand-editable ever after. Additionally, **extract the schema + interview intent out of
`create-study` into a new non-user-invocable `study-config` skill** that all consumer skills
load.

**Rationale**
- *Why hybrid, not pure (a):* a bare config file that the user must author from documentation
  is a cold-start wall for exactly the newcomers the plugin now targets. The interview removes
  that wall.
- *Why hybrid, not pure (b):* the file, not the conversation, is the durable artifact. Skills
  read the file; users edit the file directly when conventions change; version control tracks
  it. The interview is a convenience for producing it, never a gate — every field is optional
  with documented defaults, so a user who deletes or hand-writes the file loses nothing.
- *Why Markdown, not YAML/JSON:* the consumers are Claude and the user. Free-form Markdown
  sections tolerate partial answers, prose nuance ("we use 5-char codes but older studies are
  free-form"), and omitted sections — a schema validator would fight that. This also preserves
  continuity: `study-config.md` already exists in merged `main` (usage-guide, `examples`).
- *Fit with skill-writing lessons:* L3 — the interview is specified as intent ("learn enough
  about the project to fill the schema") with the schema as the target, NOT a numbered question
  script; the current working-tree `create-study` already does this correctly — preserve that
  style. L4 — after generating the config, the skill continues into its original task; it never
  stops and asks the user to re-invoke. L1 — one schema, one home (the new `study-config`
  skill); every other skill references it instead of restating it.
- *Why extract a `study-config` skill:* today `study-review` and `playwright-test` say "see the
  `create-study` skill for its schema," which forces loading a study-*creation* skill during a
  *review*, and leaves the interview bootstrappable only via `/create-study`. A user whose
  first contact is `/study-review` on an inherited study deserves the same one-time setup.
  Centralizing also fixes drift risk (L1).

**Concrete shape**

- **File:** `study-config.md`, project root. Created by whichever skill first needs it;
  hand-editable; committed to the user's project repo (their choice).
- **New skill:** `skills/study-config/SKILL.md`, frontmatter `user-invocable: false`,
  description like "Schema and first-run setup for study-config.md, the project configuration
  file read by all conscript skills." Contents, in order:
  1. One paragraph: what the file is, where it lives, that every field is optional and
     defaults apply when a field/section is absent.
  2. **The schema** — move the fenced schema block currently inlined in
     `skills/create-study/SKILL.md` (lines ~34–67) here, with ONE fix: add a `## Servers`
     section (`Local: ...` default `http://127.0.0.1:5100`; `Staging: ...`; `Production: ...`)
     — the working-tree `upload` skill already claims staging/production URLs are "recorded in
     study-config.md" but the schema has no such field. Move the Review-pipeline "Server URL"
     line into `## Servers` and have the Review-pipeline section point to it.
  3. **First-run setup**, stated as intent (mirror the current create-study wording): if no
     `study-config.md` exists when a skill needs it, interview the user to learn enough about
     the project to fill the schema — domain, typical study structure, constraints, naming
     conventions, repo/dir locations, whether they keep design docs, whether they have a
     Playwright suite; if they already have a `.md` describing their patterns, read and use
     it; write the file; **then continue with the task that triggered setup.** Skills needing
     only one or two fields (e.g. `upload` resolving a path) may instead ask just those
     questions and offer the full setup, rather than forcing the whole interview.
- **Consumers:** `create-study`, `study-review`, `playwright-test`, `upload`, `examples`,
  `coding` all reference the `study-config` skill by name and name the specific fields they
  read (the working tree already names fields; keep that — it's what makes defaults work).

## 5. Adversarial + usability review protocol (required by Marc)

Spawn a **fresh Opus agent with no implementation context** (blind to the implementer's
rationale — give it only: the branch diff, the final skill files, the `skill-writing` skill,
and Marc's one-line goal "general-purpose conscript plugin, project specifics via
study-config.md"). It produces a findings list labeled Bug/Note/Question (dogfooding the
pipeline's own taxonomy). Two mandated passes:

**(a) Adversarial correctness pass — per changed skill:**
- *Framework-claim verification (L6):* every factual claim about congame/conscript/Playwright
  behavior (e.g. "upload resolves module dependencies, so exit 0 ⇒ compiles"; Unpoly
  button/form behavior; `_anon-login` URL shape; default admin credentials
  `admin@congame.local`/`admin` from `congame-web/local.rkt`) checked against the congame
  source (locate a local checkout, e.g. via many-designs' config, or clone
  MarcKaufmann/congame shallowly).
- *Over-scripting check (L3):* flag any user-facing interview written as a rigid numbered
  question script rather than intent + target schema.
- *Hidden MD-coupling check:* re-run the §3 greps AND read for semantic coupling greps miss
  (assumptions like "two treatment arms," "groups of 2 or 4," "matched pairs" stated as
  universal rather than example).
- *Internal consistency:* config fields referenced ⇄ schema; step numbering in study-review's
  two paths; no dangling skill references (e.g. to the removed `docs`).

**(b) Usability pass — "could a new user with a different study actually use this?"**
Concrete walkthroughs, executed as tabletop simulations (reviewer role-plays the user AND
traces exactly what each skill instructs, step by step, flagging every point where required
information is unavailable, ambiguous, or assumed):
- *Persona A — newcomer, minimal project:* empty repo, solo survey study (no treatments, no
  matchmaking), no design docs, no Playwright, free-form study names. Trace `/create-study` →
  `/study-review` (must land on the checklist path) → `/upload`. Checks: does the first-run
  interview produce a valid config for a project where most Review-pipeline fields are absent?
  Does study-review degrade gracefully? Is jargon defined on first use (L5) — `-with-admin`,
  bot model, instance?
- *Persona B — MD-like project:* `experiments/`, design docs, Playwright suite with helpers,
  Co-Authored-By convention, tracking issues. Trace `/study-review` end-to-end on paper:
  every command must be constructible from config fields alone; verify the PR-pipeline commit
  order and draft/ready decision rule are unambiguous.
- *Persona C — mid-stream adopter:* user's first-ever invocation is `/study-review` on an
  inherited `.rkt` file with no config present. Verify the bootstrap path exists and doesn't
  force a `/create-study` detour.
- *Docs check:* read README + usage-guide as Persona A; can they get from "cloned the plugin"
  to "first study uploaded" without opening SKILL.md files?

**Racket-environment dependency** (a separate agent is installing it; do not plan that):
live smoke tests — actually running `/create-study` in a scratch project, `raco congame
upload` of a generated study, and one Playwright run — require the env. **If available:** run
Persona A live in a scratch dir (simulated user answers) and verify the generated study
compiles via upload. **Fallback if unavailable:** tabletop walkthroughs stand; verify
`raco congame` command syntax against congame's docs/source instead of executing; state
explicitly in the PR body which claims are untested ("not yet verified end-to-end; Racket env
pending").

Implementer triages findings (fix Bugs; fix cheap Notes; carry Questions into the PR body for
Marc), commits fixes, and appends a short "Adversarial review" section to the PR body:
findings count, what was fixed, what's left open.
